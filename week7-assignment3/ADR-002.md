# ADR-002: Add a Redis Cache Before Adding a Read Replica

| Field | Value |
|---|---|
| **Date** | 2026-09-02 |
| **Status** | Accepted |
| **Deciders** | Backend team (Phase 4 implementers) |

---

## Why This Is a Real Decision

Both a Redis cache and a PostgreSQL read replica improve read throughput, but they solve the problem differently and carry different operational costs. A cache trades consistency (stale data window) for sub-millisecond reads on hot paths. A read replica trades infrastructure complexity (a second database node, replication lag, connection routing) for transparent query offloading with no application-level invalidation logic. Choosing which to add first — or whether to add either at all — determines the complexity budget for Phase 4 and the failure modes the team must handle.

---

## Context

The following forces shape this decision. No conclusion is drawn here.

1. **One dominant read path.** The task-list endpoint (`GET /api/v1/projects/:projectId/tasks`) is hit on every project page load by every member. It is the single hottest read in the system. Other list endpoints (comments, members, tags) are accessed less frequently and on smaller datasets.

2. **Read-to-write ratio is heavily skewed.** A typical project member loads the task list many times per session but creates or updates a task only occasionally. Informal estimates place the ratio at roughly 50 reads per 1 write on the task-list endpoint.

3. **Small team, limited operational budget.** Phase 4 is built by 1–2 backend developers over three weeks. Every piece of infrastructure added (a Redis node, a PostgreSQL replica, connection routing) is another thing to configure in local development, CI, and production. The team can absorb one new dependency; two at once is risky.

4. **Latency headroom exists today.** NFR-1 requires ≤ 200 ms at p95. Current single-node PostgreSQL queries return in 20–50 ms on 10,000 rows. There is 150+ ms of headroom before the target is breached.

5. **Availability target of 99.5 %.** NFR-2 allows roughly 3.6 hours of downtime per month. A single PostgreSQL node with automated daily backups can meet this, but a hardware failure means minutes-to-hours of recovery from backup — no hot standby.

6. **Some reads must never be stale.** The membership list (`GET /api/v1/projects/:projectId/members`) drives role checks. Serving a cached membership list could let a recently removed user appear authorised. This endpoint must always hit the database.

---

## Options Considered

### Option A — Redis Cache for the Task-List Endpoint

Add a Redis instance. Cache the serialised response of `GET /projects/:projectId/tasks` keyed by `project_id` + query-parameter hash, with a 60-second TTL. Evict on any write to the `tasks` table for that project.

**Advantages:**

- Sub-millisecond reads for the hottest endpoint. A cached response skips the database entirely, freeing connection-pool slots for writes and uncacheable reads.
- Surgical: only the one endpoint that needs it gets a cache. The rest of the application stays unchanged.
- Evict-on-write keeps the stale window short (milliseconds between DB commit and cache eviction, not the full 60-second TTL).

**Disadvantages:**

- Adds Redis as a runtime dependency — another process to run locally, another service in CI, another node in production.
- Cache-invalidation logic must be manually coded in every write path (`TasksService.create()`, `.update()`, `.remove()`). A missed eviction is a silent correctness bug — stale data served until TTL expires.
- A race condition exists: a read can slip in between the database commit and the cache eviction, serving stale data for up to one TTL cycle. Not harmful for a task list, but the window exists.

### Option B — PostgreSQL Streaming Read Replica

Add a second PostgreSQL instance as a streaming replica. Route all read-only queries (list endpoints) to the replica via a separate read-only connection pool. Writes stay on the primary.

**Advantages:**

- No manual invalidation logic. The replica receives changes automatically via the replication stream. Every query is a real SQL query — no cache-key design, no eviction paths to maintain.
- Acts as a warm standby for failover, directly improving the 99.5 % uptime target (NFR-2). Promotion to primary on failure takes seconds, not the minutes-to-hours of a backup restore.
- All list endpoints benefit, not just the task list.

**Disadvantages:**

- Asynchronous replication lag means the replica may be up to several hundred milliseconds behind the primary. A user who creates a task and immediately reloads may not see it — the "read-your-writes" problem.
- "Read-your-writes" routing (send recent writers to the primary for 2 seconds) adds application-level complexity comparable to cache invalidation.
- Doubles database infrastructure: a second PostgreSQL node, replication configuration, monitoring for lag, connection-pool management for two hosts.
- Does not help with CPU-bound queries — both nodes execute the same SQL. A cache avoids query execution entirely.

### Option C — Do Neither (Single PostgreSQL, No Cache, No Replica)

Ship Phase 4 with a single PostgreSQL node and no caching layer. Add infrastructure only when a measured performance problem appears.

**Advantages:**

- Simplest possible architecture. Zero operational overhead beyond the primary database.
- Fastest to develop: no cache-invalidation code, no replica routing, no new dependencies.
- The 200 ms latency budget has 150+ ms of headroom at current query times — there is no measured problem to solve.

**Disadvantages:**

- No path to improved read throughput without future rework. If traffic doubles unexpectedly, the team must add infrastructure under pressure.
- Single point of failure: a hardware failure means downtime and a restore from backup, straining the 99.5 % uptime target.
- Every read hits the primary, competing with writes for the same connection pool. Under sustained load, write latency increases because reads consume connection slots.

---

## Decision

**Option A — add a Redis cache for the task-list endpoint**, implemented in Phase 4. The read replica (Option B) is deferred to a later phase when the 99.5 % uptime SLA requires a hot standby.

**Criterion:** the team has capacity for one new infrastructure dependency in Phase 4. The dominant performance concern is the task-list endpoint, which is both the hottest read and the one most tolerant of brief staleness (a task appearing one second late in a list is not harmful). A cache targets this specific endpoint with sub-millisecond reads and a well-defined eviction strategy. A read replica solves a broader problem (all reads + availability) but at roughly double the infrastructure and operational cost, solving a performance problem that does not yet exist (queries are 4× faster than the budget). The cache delivers the highest read-throughput improvement per unit of complexity.

---

## Consequences

**For the code:**

- `TasksService` gains cache-read and cache-eviction calls around the three write methods (`create`, `update`, `remove`). Each calls `cache.del(tasks:project:${projectId}:*)` before returning. This is ~5 lines of code per method.
- A `CacheModule` wrapping a Redis client is added to the NestJS dependency graph. The cache key pattern is `tasks:project:<projectId>:<queryHash>` with a 60-second TTL.
- The membership endpoint (`GET /projects/:projectId/members`) is explicitly **not** cached, because stale membership data would compromise role-based access control.

**For the team:**

- Local development requires a running Redis instance (a single `docker run redis` command or `docker-compose` entry). CI adds one service container.
- The eviction contract must be documented: any new write path that touches the `tasks` table must call the eviction helper. Code review should check for this.

**For the user:**

- Task-list page loads are faster under concurrent traffic (cache hit returns in < 1 ms vs 20–50 ms from PostgreSQL).
- A brief stale window (< 1 second in practice, due to evict-on-write) means a newly created task may not appear in another member's list for up to one second. This is imperceptible in normal usage.

**Negative consequence accepted:**

- A missed cache eviction (e.g. a new write path added without calling the eviction helper) silently serves stale data for up to 60 seconds. **Mitigation:** the eviction helper is a single function call; code-review checklists and integration tests that assert cache invalidation after writes reduce this risk.
- Redis becomes a runtime dependency. If Redis is down, the application must fall back to direct database queries (cache-aside pattern). The service must handle Redis connection failures gracefully — a `try/catch` around every cache call — to avoid cascading failures.

---

## Expiry Condition

Revisit this ADR if **the 99.5 % uptime SLA becomes contractually binding** (e.g. an external client depends on the API), requiring a hot-standby failover that only a read replica provides. Also revisit if **more than three list endpoints need caching** — at that point, the per-endpoint cache-eviction logic becomes a maintenance burden, and a replica that transparently handles all reads may have lower total cost of ownership.
