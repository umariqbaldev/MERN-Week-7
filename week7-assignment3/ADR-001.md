# ADR-001: Use Offset (Page-Based) Pagination for List Endpoints

| Field | Value |
|---|---|
| **Date** | 2026-09-02 |
| **Status** | Accepted |
| **Deciders** | Backend team (Phase 4 implementers) |

---

## Why This Is a Real Decision

Both offset and cursor pagination are production-grade strategies with genuine trade-offs. Offset supports numbered page controls and a total count, which simplifies the frontend, but its query cost grows linearly with page depth. Cursor pagination is O(1) at any depth but cannot jump to an arbitrary page or report a total count. Neither is obviously superior — the right choice depends on dataset size, access patterns, and what the UI needs to show.

---

## Context

The following forces shape this decision. No conclusion is drawn here — that comes in the Decision section.

1. **Frontend page-number requirement.** The Next.js task-list view must show "142 tasks — page 3 of 8" and let users click any page directly. This requires a `total` count and a `totalPages` value in every list response. Cursor pagination cannot provide either without a separate `COUNT(*)` query.

2. **Bounded dataset size.** Tasks belong to a project, comments belong to a task, members belong to a project. The largest expected collection is a single project's task list, which NFR-1 sizes at ≤ 10,000 rows. No list endpoint serves the entire database — the scope is always filtered by a parent entity.

3. **Latency budget has headroom.** NFR-1 requires ≤ 200 ms at p95 for the first page. Current PostgreSQL query benchmarks on 10,000 rows with an indexed `project_id` filter return in 20–50 ms. Even `OFFSET 5000` on this dataset completes in under 100 ms. The budget is not tight.

4. **Six list endpoints share one convention.** Tasks, projects, users, project members, tags, and comments all need pagination. A single convention defined once in the API contract (api-spec.md § 1.3) is cheaper to implement and document than mixing two styles. Whichever approach is chosen, it must work uniformly for all six resources.

5. **Migration cost is high.** Changing pagination style after Phase 4 ships means a breaking API change — different query parameters (`page` / `pageSize` vs `cursor` / `limit`), a different response shape (no `meta.total` vs a `nextCursor` field), and frontend rework. The choice made now locks in the contract for the life of `/api/v1`.

---

## Options Considered

### Option A — Offset (Page-Based) Pagination

Every list endpoint accepts `page` (1-indexed) and `pageSize` (max 100) and returns `{ data, meta: { page, pageSize, total, totalPages } }`.

**Advantages:**

- Supports "jump to page N" — the frontend can render numbered page links, a "last page" button, and "showing 1–20 of 142 tasks" without additional requests.
- Simple to implement: `SELECT ... LIMIT $pageSize OFFSET ($page - 1) * $pageSize` plus a `COUNT(*)` for `total`. TypeORM's `findAndCount()` does both in one call.
- The `total` count doubles as a lightweight metric — dashboards and summary views ("this project has 142 tasks") need no extra query.

**Disadvantages:**

- Performance degrades linearly with page depth. `OFFSET 50,000` forces PostgreSQL to scan and discard 50,000 rows before returning the page. On a table with 100,000 rows, deep pages can exceed 200 ms.
- The `COUNT(*)` adds overhead to every list query. On unindexed or heavily filtered queries, the count alone can be expensive.
- Concurrent inserts between page fetches can cause items to shift — a row may appear twice or be skipped entirely across two consecutive page requests.

### Option B — Cursor (Keyset) Pagination

Every list endpoint accepts `cursor` (an opaque token encoding the last seen sort key) and `limit`, and returns `{ data, nextCursor }`.

**Advantages:**

- Constant performance at any depth — page 10,000 is as fast as page 1, because the database seeks by index (`WHERE id > :lastId LIMIT :limit`) instead of scanning and discarding rows.
- No `COUNT(*)` overhead per request.
- Immune to the "shifting rows" problem — each page starts from a stable anchor point, so concurrent inserts never cause duplicates or skips.

**Disadvantages:**

- Cannot jump to an arbitrary page. The client must page forward sequentially, passing `nextCursor` from each response. A "go to page 47" button is not possible.
- No `total` or `totalPages` in the response. The UI cannot show "page 3 of 8" or a progress bar without a separate count query (which would negate the performance advantage).
- Harder to implement on compound sort keys. Sorting by `priority DESC, createdAt ASC` requires encoding both values into the cursor and building a multi-column `WHERE` clause — more error-prone than a simple `OFFSET`.

---

## Decision

**Offset (page-based) pagination**, applied uniformly to all six list endpoints via the convention defined in api-spec.md § 1.3.

**Criterion:** the largest dataset any single list endpoint serves is a project's task list, bounded at ~10,000 rows by NFR-1. At that scale, `OFFSET` + `COUNT(*)` completes well within the 200 ms p95 budget (measured at 20–50 ms for page 1, under 100 ms for `OFFSET 5000`). The frontend needs `total` and page numbers for the task-backlog UI — cursor pagination cannot provide these without re-adding the `COUNT(*)` query that is its main selling point to avoid. Offset's depth-penalty disadvantage is real but does not materialise at the current dataset sizes.

---

## Consequences

**For the code:**

- Every list endpoint returns `{ data, meta: { page, pageSize, total, totalPages } }`. A single reusable `PaginationDto` and `paginate()` helper in the repository layer handles this for all six resources.
- TypeORM's `findAndCount()` method is the standard query pattern — one call, two results (rows + total), no cursor-encoding logic.

**For the team:**

- The API contract is uniform and simple. Frontend developers can build one `usePagination()` hook that works with every list endpoint.
- No need to design cursor-encoding/decoding logic or handle compound sort-key cursors.

**For the user:**

- The task list shows page numbers, a total count, and supports direct page navigation — a familiar pattern from most web applications.

**Negative consequence accepted:**

- If any project's task list grows past ~50,000 rows, deep-page requests (page > 500) will breach the 200 ms latency target. **Mitigation:** the `pageSize` maximum of 100 and realistic project sizes (hundreds to low thousands of tasks) make this unlikely within the application's intended use. If it happens, cursor pagination can be introduced as a `/api/v2` endpoint for the task-list resource specifically, without breaking `/api/v1` consumers.
- Every list query pays the cost of `COUNT(*)` for the `total` field. On the current indexed dataset sizes, this adds ~1–5 ms per query — negligible against a 200 ms budget.

---

## Expiry Condition

Revisit this ADR if **any single project accumulates more than 50,000 tasks**, or if **p95 latency for `GET /api/v1/projects/:projectId/tasks` at page depths beyond 100 exceeds 150 ms** in production monitoring. At that point, the offset scan cost dominates and cursor pagination should replace offset for task-list endpoints, shipped behind `/api/v2` to avoid breaking existing consumers. The remaining five list endpoints (projects, users, members, tags, comments) are unlikely to reach this scale and can stay on offset pagination.
